Inheritance
Write once. Reuse everywhere. Extend when needed.

The Big Idea

Inheritance lets one class get all the attributes and methods of another class for free — no copy-paste required.

class Animal:                    # PARENT / base class
    def __init__(self, name):
        self.name = name
    def eat(self):
        print(f"{self.name} is eating.")

class Dog(Animal):               # CHILD — inherits Animal
    def bark(self):
        print(f"{self.name} says: Woof!")

rex = Dog("Rex")
rex.eat()    # inherited → Rex is eating.
rex.bark()   # Dog's own → Rex says: Woof!
class Child(Parent):
child gets ALL parent methods FREE
IS-A relationship: Dog IS-A Animal

Why Inheritance? — Don't Repeat Yourself 🧬

WITHOUT INHERITANCE — DUPLICATION
class Dog:
    def __init__(self, name): self.name = name
    def eat(self):              # DUPLICATED ❌
        print(f"{self.name} eats.")
    def bark(self):
        print("Woof!")

class Cat:
    def __init__(self, name): self.name = name
    def eat(self):              # DUPLICATED ❌
        print(f"{self.name} eats.")
    def meow(self):
        print("Meow!")
⚠️ eat() is copy-pasted. Add 10 more animals → 10 copies of eat(). Fix a bug in eat() → update 10 files. This is the DRY violation.
WITH INHERITANCE — SINGLE SOURCE OF TRUTH
class Animal:               # shared code lives HERE
    def __init__(self, name):
        self.name = name
    def eat(self):            # written ONCE ✅
        print(f"{self.name} eats.")

class Dog(Animal):
    def bark(self): print("Woof!")

class Cat(Animal):
    def meow(self): print("Meow!")

# Dog and Cat BOTH have eat() — from Animal — zero copies!
✅ eat() lives in ONE place. Add 10 animals — they all get eat() free. Fix the bug once → fixed everywhere.
Animal = parent / base / super class
Dog, Cat = child / derived / sub class
DRY = Don't Repeat Yourself

super() & Method Overriding 🧬

super() — EXTEND THE PARENT'S __init__
class Animal:
    def __init__(self, name, age):
        self.name = name
        self.age  = age

class Dog(Animal):
    def __init__(self, name, age, breed):
        super().__init__(name, age)  # ← run parent first
        self.breed = breed         # ← add Dog's own attr

rex = Dog("Rex", 3, "Labrador")
print(rex.name)   # Rex   ← from Animal
print(rex.breed)  # Labrador ← from Dog
Rule: always call super().__init__() first, then add your own attributes below it.
METHOD OVERRIDING — REPLACE THE PARENT'S VERSION
class Animal:
    def speak(self):
        print("... (some sound)")

class Dog(Animal):
    def speak(self):     # OVERRIDES parent!
        print("Woof!")

class Cat(Animal):
    def speak(self):     # OVERRIDES parent!
        print("Meow!")

class Fish(Animal):
    pass                # no override → uses parent's

Dog().speak()   # Woof!
Cat().speak()   # Meow!
Fish().speak()  # ... (some sound)
💡 isinstance(rex, Animal) → True   |   isinstance(rex, Dog) → True   |   isinstance(rex, Cat) → False

isinstance() & issubclass() — Checking the Hierarchy 🧬

THE CLASS HIERARCHY
Vehicle
└── Car
└── ElectricCar
class Vehicle: pass
class Car(Vehicle): pass
class ElectricCar(Car): pass

my_car = ElectricCar()
CHECKING MEMBERSHIP
isinstance(my_car, ElectricCar) → True   direct class
isinstance(my_car, Car) → True   parent
isinstance(my_car, Vehicle) → True   grandparent
isinstance(my_car, str) → False   unrelated
 
issubclass(ElectricCar, Car) → True
issubclass(Car, ElectricCar) → False   reversed!
💡 isinstance() checks if an object is an instance of a class OR any of its ancestors. Safer than type(obj) == Car which only matches exactly.

Polymorphism
One interface — many forms of behaviour

The Big Idea

Poly = many   Morph = forms.
Different classes share the same method name, but each provides its own behaviour. The caller doesn't need to know which type it's talking to.

animals = [Dog("Rex"), Cat("Luna"), Parrot("Tweety")]

for animal in animals:
    print(animal.speak())   # same call — different result!

# Rex says: Woof!
# Luna says: Meow!
# Tweety says: Tweet!
same method name → different behaviour
caller doesn't care about the type
works with ANY object that has .speak()

Polymorphism in Action — Shapes 🎭

PARENT DEFINES THE INTERFACE
class Shape:
    def __init__(self, colour):
        self.colour = colour
    def area(self):                # meant to be overridden
        return 0
    def describe(self):           # uses self.area() — polymorphic!
        print(f"{self.colour} area = {self.area():.2f}")

class Circle(Shape):
    def __init__(self, colour, r):
        super().__init__(colour); self.r = r
    def area(self):                # OVERRIDES Shape.area()
        return 3.14159 * self.r ** 2

class Rectangle(Shape):
    def __init__(self, colour, w, h):
        super().__init__(colour); self.w=w; self.h=h
    def area(self): return self.w * self.h
ONE LOOP — EVERY SHAPE CALCULATED CORRECTLY
shapes = [
    Circle("red", 5),
    Rectangle("blue", 4, 6),
]

for s in shapes:
    s.describe()  # calls s.area() — which version?
                  # whichever belongs to THAT object!

# red area = 78.54   ← Circle.area()
# blue area = 24.00  ← Rectangle.area()
💡 describe() is defined once in Shape. It calls self.area() — Python automatically picks the most specific version for each object.
override area() in each shape
describe() never changes

Duck Typing — Python's Natural Polymorphism 🦆

"If it walks like a duck and quacks like a duck — it's a duck."
Python doesn't care about the class name. If an object has the right method, Python calls it. No inheritance required.

NO SHARED PARENT — STILL WORKS
class Printer:
    def render(self):
        print("Printing document...")

class Screen:
    def render(self):
        print("Displaying on screen...")

class PDFExporter:
    def render(self):
        print("Exporting to PDF...")

def show_output(device):
    device.render()   # works for ANY object with render()

outputs = [Printer(), Screen(), PDFExporter()]
for d in outputs:
    show_output(d)   # same call — different output!
KEY IDEAS
Duck typing = Python checks if the method exists at call time, not at class-definition time.
No inheritance needed. As long as the object has .render(), the function works. Period.
vs Inheritance-based polymorphism: that requires a shared parent. Duck typing is more flexible — any object qualifies.
Python built-ins use duck typing too: len() works on any object with __len__. for works on any object with __iter__.

Abstraction
Define what. Hide how.

The Big Idea

Abstraction = showing only what matters, hiding the complexity underneath.
You press the gas pedal — you don't see the engine internals. You call .pay() — you don't know if it's a card or PayPal.

Abstract class — defines the CONTRACT (what you must implement). Cannot be instantiated.
Abstract method — must be implemented by every subclass. Marked with @abstractmethod.
Concrete class — inherits the abstract class and fills in all abstract methods.
from abc import ABC, abstractmethod
class MyClass(ABC):
@abstractmethod

Abstract Base Class — Enforcing a Contract 🫙

DEFINE THE ABSTRACT CLASS
from abc import ABC, abstractmethod

class PaymentMethod(ABC):       # ← abstract class
    @abstractmethod               # ← subclass MUST implement
    def pay(self, amount):
        pass

    @abstractmethod
    def refund(self, amount):
        pass

# PaymentMethod() → TypeError: can't instantiate abstract class!

class CreditCard(PaymentMethod):
    def pay(self, amount):
        print(f"Card charged ${amount}")
    def refund(self, amount):
        print(f"Card refund ${amount}")

class PayPal(PaymentMethod):
    def pay(self, amount):
        print(f"PayPal sent ${amount}")
    def refund(self, amount):
        print(f"PayPal refund ${amount}")
THE CALLER DOESN'T CARE HOW IT WORKS
def checkout(payment: PaymentMethod, total):
    payment.pay(total)    # no idea HOW it pays
                          # trusts the contract!

checkout(CreditCard(), 99.99)
# Card charged $99.99

checkout(PayPal(), 49.99)
# PayPal sent $49.99
💡 Missing an abstract method? Python raises a TypeError the moment you try to instantiate the class — catching the error at startup, not in production.
✅ Contract = guaranteed interface
✅ Caller doesn't care which payment method
✅ Add a new method without changing checkout()

Dunder Methods

Dunder = Double UNDERscore. When you call print(obj), Python actually calls obj.__str__(). Define these methods in your class to make objects behave like built-in types.

a == b → a.__eq__(b)

Special Methods in Practice ✨

__str__ AND __repr__
class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages

    def __str__(self):    # for print()
        return f'"{self.title}" ({self.pages} pages)'

    def __repr__(self):   # for repr() / debugger
        return f'Book({self.title!r}, {self.pages})'

b = Book("1984", 328)
print(b)        # "1984" (328 pages)
print(repr(b))  # Book('1984', 328)
__len__, __eq__, __add__
class Library:
    def __init__(self):
        self.books = []
    def add(self, title):
        self.books.append(title)
    def __len__(self):            # enables len()
        return len(self.books)
    def __contains__(self, t):  # enables `in`
        return t in self.books

lib = Library()
lib.add("1984"); lib.add("Dune")

print(len(lib))          # 2
print("Dune" in lib)    # True

All 4 Pillars Together — Animal Kingdom 🏛️

from abc import ABC, abstractmethod

class Animal(ABC):               # ABSTRACTION
    def __init__(self, name):
        self.name    = name        # ENCAPSULATION
        self.__health = 100       # private!

    @abstractmethod
    def speak(self):              # contract — must implement
        pass

    def eat(self):
        print(f"{self.name} eats.")

    def __str__(self):            # SPECIAL METHOD
        return f"{type(self).__name__}({self.name})"


class Dog(Animal):               # INHERITANCE
    def speak(self):              # POLYMORPHISM
        return f"{self.name}: Woof!"

class Cat(Animal):               # INHERITANCE
    def speak(self):              # POLYMORPHISM
        return f"{self.name}: Meow!"
# Polymorphism — one loop for all animals:
animals = [Dog("Rex"), Cat("Luna")]

for a in animals:
    print(a)           # __str__: Dog(Rex)
    print(a.speak())    # POLYMORPHISM
    a.eat()             # INHERITED from Animal
Encapsulation — self.__health is private
Inheritance — Dog & Cat get eat() from Animal
Polymorphism — same speak() call → different result
Abstraction — Animal(ABC) + @abstractmethod

Encapsulation vs Abstraction — Don't Confuse Them 🔍

ENCAPSULATION
HOW you package and protect data.
Bundles data + methods. Hides internal state with private attributes.
Analogy: the engine bay of a car is sealed. You can't directly touch the pistons — only interact via the interface (gas pedal). 
self.__balance = 0    # private = encapsulation
def get_balance(self):
    return self.__balance
ABSTRACTION
WHAT the object can do (the contract). Hides the implementation — caller uses simple interface.
Analogy: the dashboard shows speed and fuel level. You don't see RPMs, fuel injection timings, torque curves. Just the relevant interface. 
@abstractmethod       # ← abstraction
def pay(self, amount):
    pass              # subclass fills this in
💡 They often appear together: Encapsulation bundles and protects data within a class. Abstraction defines the interface that outside callers use. Together they make classes that are safe internally AND easy to use externally.

Common Mistakes — Don't Fall For These! ⚠️

❌ Forgetting super() in child __init__
class Dog(Animal):
  def __init__(self, name, breed):
    self.breed = breed ← name never set!
# Fix: call super().__init__(name) first
❌ Instantiating an abstract class
p = PaymentMethod() ← TypeError! ❌
p = CreditCard() ← correct ✅
Abstract classes are templates — you create the concrete subclasses.
❌ Skipping an abstract method
class BadPay(PaymentMethod):
  def pay(self, amount): ... ← ok
  # forgot refund() → TypeError on creation!
❌ Confusing method override with super()
def speak(self): ← overrides completely
  super().speak() ← use this to also run
  print("Woof!")    the parent's version
❌ Missing __str__ → useless print output
print(obj) → <__main__.Dog at 0x7f...>
# Add __str__ to get readable output
❌ type() instead of isinstance() for subclasses
type(rex) == Animal → False ❌ (rex IS a Dog)
isinstance(rex, Animal) → True ✅
